    The Problem Everyone Fears

    You discover your system was accessed by an adversary. 10,268 requests through 3,075 rotating IPs. They hit your most sensitive repository â€” the one with investigation methodology, FOIA planning, evidence provenance chains, and personal information about public officials.

    845 requests hit that repository.

    The question that follows every breach: what did they get?

    Most systems can’t answer this. Access logs show requests and status codes. If the status code is 200, the assumption is: they got the content. If the repository had 845 successful responses, the assumption is 845 documents leaked. If those documents contained PII, the assumption is PII leaked. Notification requirements trigger. Panic follows.

    We didn’t have to assume. We could count.

    How We Knew

    This audit was possible because the defense architecture creates a forensic trail as a side effect of defense. Every layer that processes a request also classifies what the request received.

    Layer 1: The Access Log (What Was Requested)

    Caddy’s structured access logs record every request with:

    • Timestamp (UTC, millisecond precision)
    • Host, path, method, status code
    • User-Agent, Accept-Language, Accept-Encoding
    • Response size, response time
    • Upstream handler (which layer processed the request)

    The upstream handler is the critical field. It tells us not just that a request returned 200, but which system served that 200:

    Upstream HandlerWhat It Means
    reverse_proxy localhost:3000Real Forgejo â€” actual content served
    reverse_proxy localhost:9753Scatter server â€” fabricated content
    respondStatic response (403, challenge page, API block)
    file_serverStatic assets (CSS, JS, images)

    When the log shows 200 with handler localhost:9753, we know with certainty: the requester received scatter poison, not real content. No ambiguity. No assumption required.

    Layer 2: The Scatter Server (What Was Served)

    The scatter server at localhost:9753 is deterministic. Given the same request path and the same seed, it produces the same fabricated HTML every time. This means:

    1. We can reconstruct what was served. For any request path in the log, we can regenerate the exact scatter response the fleet received.
    2. We can verify it contains no real data. The scatter server has no access to Forgejo’s database, no access to git repositories, no access to any real content. It generates HTML from a pseudorandom number generator seeded by the path string. It cannot leak real data because it has never seen real data.
    3. We can measure the poison ratio. By counting scatter-handler responses vs Forgejo-handler responses, we get an exact ratio of fabricated to real content served.

    The scatter server is not a proxy that sometimes serves real content. It is a standalone program that generates fictional content from mathematical functions. The separation is architectural, not configurational.

    Layer 3: Forgejo Access Control (What Could Have Leaked)

    For the 3 requests that reached real Forgejo, we can audit what Forgejo would serve to an unauthenticated visitor:

    • Private repositories: 404 (Forgejo returns nothing for anonymous access)
    • Public repository root: The listing page â€” repository name, description, last-updated timestamp, navigation chrome
    • Public repository content: Source trees, commits, diffs, issues, wiki â€” but only if the URL pattern reaches those handlers

    The 3 real Forgejo responses were all repository root pages â€” shallow listing pages that show the same information visible on the explore page. The fleet never reached deep content on any real Forgejo handler because the deep content paths were already covered by scatter routing (the original regex-based defense worked for most paths â€” only the gap paths fell through to real Forgejo, and those gap paths were navigational, not content-bearing).

    Layer 4: Content-Level Verification (What’s Actually In There)

    The final audit layer: examining the actual content of the repositories the fleet targeted. whitePaper is the investigation workspace. It contains:

    • FOIA request drafts and response analysis
    • Evidence provenance chains (public record ? analysis ? publication path)
    • Investigation methodology documents
    • Network analysis (funding flows, board relationships, entity connections)
    • Personal information about public officials (names, titles, voting records â€” all public record, but organized and cross-referenced)

    None of this content appears in scatter output (the scatter server has never read these files). None of it appears in Forgejo’s listing page response (listing pages show repository metadata, not file contents). The 845 requests produced 0 content exposures.

    The Forensic Stack

    This creates a four-layer forensic stack that runs without any additional instrumentation:

    Each layer narrows the exposure surface. The access log gives the universe of requests. The handler classification separates real from fabricated. The application access control determines what real responses could contain. The content verification confirms whether sensitive material was reachable.

    This stack exists as a side effect of the defense architecture. We didn’t build forensic tooling. We built defense layers, and the defense layers produce forensic evidence as exhaust.

    The Principle: Defense Creates Observability

    Traditional security monitoring adds observability to existing systems: SIEM agents, log aggregators, IDS sensors, DLP proxies. These are bolted on. They can be misconfigured, overwhelmed, or bypassed. They monitor the system but are not the system.

    The defense-as-observability model is different:

    TraditionalDefense-as-Observability
    Separate monitoring infrastructureDefense layers ARE the monitoring
    Can be disabled independentlyDisabling monitoring disables defense
    Logs what happenedLogs what happened AND what was served
    Answers “was there access?”Answers “what did they get?”
    Requires correlation across toolsSingle log line tells the full story
    After-the-fact analysisReal-time classification at request time

    When the scatter server handles a request, three things happen simultaneously:

    1. The adversary receives fabricated content (defense)
    2. The access log records the scatter handler (observability)
    3. Real content is never touched (containment)

    There is no gap between “defend” and “observe” because they are the same operation.

    What This Means Before Encryption at Rest

    This is the insight: you don’t need encryption at rest to know what was exposed, if your defense architecture classifies at the access layer.

    Encryption at rest protects data if the storage medium is physically compromised â€” stolen disk, breached database, exfiltrated backup. That’s important. Build it. Deploy it.

    But encryption at rest does not tell you what was served. A fully encrypted database that decrypts at query time still serves real data to authenticated (or insufficiently authenticated) requesters. If an adversary accesses the application layer â€” through API gaps, session hijacking, credential stuffing, or (as in our case) a membrane gap that allows unauthenticated access to application routes â€” encryption at rest is irrelevant. The data was decrypted and served.

    The forensic question is not “was the data encrypted on disk?” but “what did the response contain?” And that question is answered by the access layer, not the storage layer.

The fleet bypassed the CaddyBridge posture routing (rotating IPs) and the deep-content regex (finding gap paths) â€” but the scatter server still caught 842 of their 845 whitePaper requests.

    99.6% catch rate on the most sensitive repository, from a defense layer the fleet never knew existed.

    The Privacy Constraint

    Everything described here operates without storing IP addresses.

    The access log records User-Agent, Accept-Language, Accept-Encoding, request path, response handler, and timing. It does not record source IP. The behavioral hash (49e77ea75aa7666e) is computed from request population patterns â€” User-Agent distribution, header consistency, inter-request timing, static asset ratio â€” not from IP addresses.

    The forensic audit answered “what did the fleet get?” without ever answering “who was in the fleet?” The defense doesn’t need to know who is attacking to know what they received. Handler classification is request-scoped, not identity-scoped.

    This is deliberate. The system documents evidence of public fund misuse and civil rights violations in Detroit. Visitor privacy is non-negotiable â€” for investigators, witnesses, journalists, and even adversaries. We defend the content, not against the person. The person is irrelevant. The request is what matters.

    The Broader Pattern

    The forensic observability capability described here generalizes:

    Any system that routes adversary requests to a separate handler automatically creates a forensic trail.

    The handler separation doesn’t have to be a scatter server. It could be:

    • A CDN edge that serves cached (potentially stale) content
    • A read replica that serves a limited data view
    • A static mirror that serves a frozen snapshot
    • A sanitized API that strips sensitive fields
    • A rate-limited proxy that serves partial results

    What matters is that the handler is architecturally separate from the authoritative data source. When requests are classified and routed at the access layer, the routing decision itself is the forensic record.

    The question “what did they get?” becomes trivially answerable: they got whatever that handler serves. And if that handler has never seen the sensitive data, the answer is: nothing.

    Validation

    On October 6, 2026, this wasn’t theoretical. A real adversary fleet made 845 real requests to our most sensitive repository. We conducted a real forensic audit. The audit took minutes, not days, because the defense architecture had already classified every request at service time.

    842 scatter poison. 3 empty shells. 0 documents. 0 PII.

    The fleet operator â€” whoever they are â€” now has 845 pages of fabricated HTML that looks like it came from a real Forgejo instance. If they parse it, they’ll find plausible but wrong information. If they train on it, they’ll learn fictional relationships between fictional entities. If they try to use it for intelligence about the investigation, they’ll be operating on poisoned data.

    The defense didn’t just prevent the leak. It created a situation where the adversary believes they succeeded while holding nothing of value. In biological terms: the pathogen consumed the decoy antigen and reported back to the colony that the host is edible. The colony will send more foragers. The foragers will find more decoys. The host is untouched.

    To Builders

    If you’re building systems that hold sensitive data:

    1. Separate your handlers. Don’t serve real and fabricated content from the same process. Architectural separation makes forensic classification trivial and eliminates a class of configuration bugs where the fabricated handler accidentally accesses real data.

    2. Log the handler, not just the status. A 200 from your real application and a 200 from your decoy server mean completely different things. If your access log only records the status code, you lose the forensic trail.

    3. Make your decoy deterministic. Seed the fabrication from the request path so the same request always gets the same fake response. This prevents adversaries from detecting the decoy by requesting the same path twice and comparing results. It also means you can reconstruct exactly what was served during an audit.

    4. Don’t wait for encryption. Encryption at rest is necessary infrastructure. Build it. But don’t wait for it before building access-layer classification. The forensic question is “what was served?” not “was it encrypted on disk?” Answer the question your incident response team will actually ask.

    5. Let defense create observability. Every defense decision (route to scatter, route to real, block, challenge, tarpit) is a classification event. Log it. When the breach postmortem happens, your defense log IS your forensic record.
